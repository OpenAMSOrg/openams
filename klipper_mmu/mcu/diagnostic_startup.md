# Hosted diagnostic startup

This is the firmware connection for explicit, default-off diagnostic startup on STM32H723 and constrained STM32F207/F405/F407/F765/H743/H750 profiles. The source is built only when `KLIPPER_MMU_DIAGNOSTIC_STARTUP=y`. A disabled build adds no command, constant, task, shutdown hook, or state, and it leaves `KLIPPER_MMU_ACTUATION=0`. The enabled source publishes `KLIPPER_MMU_DIAGNOSTIC_STARTUP=1`.

`KLIPPER_MMU_ACTUATION_OPT_IN=y` is a separate experimental **software permission**. It publishes `KLIPPER_MMU_ACTUATION=1`; the default remains 0. It requires this diagnostic startup, a target-specific identity provider, configured pins, local GPIO and shared TMC UART through the startup dependencies. F207/F405/F407/F765 are limited to the one-lane Custom/1 or four-lane NightOwl/4 passive switched-buffer profiles. Powered rewind additionally requires local paired hardware PWM. DiffA/DiffB additionally requires validated calibration delivered by the host before startup and is not available on these F4x5 profiles. Do not flash or use an opt-in image for motion before a physical qualification on the exact MCU, board, wiring, motors, drivers and mechanism. That gate must measure inactive output levels, pin routing and conflicts, current limits, STEP pulse timing under interrupt load, safe-off and fault response, then record the results. `ACTUATION=1` reports a build choice, not evidence of that qualification.

## Software checks

The H723 Kconfig gate requires `MACH_STM32H723` and its explicit identity option. F207 requires USB serial on PA11/PA12 at 120 MHz. F405/F407 require USB serial on PA11/PA12 at 168 MHz; F765 requires the same USB pins at 216 MHz; H743 and H750 require them with a crystal at 400 and 480 MHz respectively. These passive targets allow one Custom lane or four NightOwl lanes, passive rewind, and switched-buffer sensing. Both require `KLIPPER_MMU_PIN_CONFIG`, `WANT_GPIO_LOCAL`, `KLIPPER_MMU_TMC_UART_SHARED`, and a target-specific identity option; optional DiffA/DiffB sensing additionally requires local ADC. The profile gates select local GPIO and shared TMC UART driver support when appropriate; pin assignments and F4x5 identity remain explicit. The shared RNG identity provider verifies the live F4 or F7 PLL fields and waits for the PLL system clock before it takes the AHB2 RNG clock. It fails closed if the clock is incompatible or already owned, times out, or sees RNG health/continuous-test errors. The F207/F405/F407/F765 RNG is read using CMSIS register definitions from the pinned Klipper tree, with the AHB2 clock sequence checked against STM32F405/F407 support and RM0090. The F4x5 profile gate is also enforced in the provider source so a forced `.config` cannot bypass it.

`KLIPPER_MMU_DIAGNOSTIC_TIMEOUT_US` is one deadline from 1000 to 1000000 microseconds, default 1000000. That full window starts at the first trigger and includes clock wait, identity wait, and board setup. It stays inside the raw 32-bit timer half horizon (2^31 ticks) at 520 MHz. A compile-time check rejects an out-of-range timeout or a tick conversion that does not fit that half range. Menu limits are not the only check.

`km_diagnostic_start` has no arguments and no immediate reply. The first valid command latches the attempt and a raw `timer_read_time()` stamp, moves `IDLE` to `WAITING`, arms a one-millisecond wake timer, and wakes `km_diagnostic_task`. The handler does not reserve pins, program peripherals, or attach the core. Another start in `WAITING`, `READY`, or `FAULTED` does nothing: no new deadline, no extra wake, no identity reset, no claim release, no fault clear, and no motion permission.

With `KLIPPER_MMU_BOOT_IDENTITY_HOST=y` the build registers `km_diagnostic_start_host epoch_hi=%u epoch_lo=%u` instead, publishes `KLIPPER_MMU_BOOT_IDENTITY_HOST=1`, and does not register `km_diagnostic_start`. The first nonzero 64-bit epoch received while unbound and `IDLE` becomes the identity and starts the same shared attempt. A zero epoch latches `FAULTED` with `KM_ERR_INVALID_PARAM` and never starts. Any later epoch (in `WAITING`, `READY`, `FAULTED`, or after shutdown) is ignored; nothing reopens the binding before an MCU reset. No hardware provider is linked and there is no RNG, timer, or constant fallback. The source gate admits this option on STM32 only with an existing target profile gate (H723, F207, F405/F407/F429, F765, G431/G474, H743/H750), rejects it together with any hardware provider, and still applies the Custom/1 or NightOwl/4 profile check. It relaxes only the RNG clock/USB constraints; pin, GPIO, and TMC gates are unchanged. See [host epoch integration](../docs/host-epoch-integration.md).

There is no `DECL_INIT` hook. Init runs before the host has finished ordinary Klipper configuration, so it is not a safe hardware trigger. The opt-in host integration places a validated DiffA/DiffB calibration object in an ordinary OID config command before finalize when `diff_calibration_file` is set, then sends this start command through public `add_config_cmd(..., is_init=True)` after ordinary Klipper configuration, including `RESERVE_PINS` (MMU pins, transport, crystal), aliases, and `BUS_PINS`. The calibration command contributes to the config CRC. This is a trusted-host boundary. This file does not take a census of MCU clients and does not create a new authorization step.

`km_diagnostic_query challenge=%u` is `HF_IN_SHUTDOWN` and read-only. The reply is exactly `km_diagnostic_state challenge=%u state=%c result=%i`. `%c` is the state enum (`IDLE=0`, `WAITING=1`, `READY=2`, `FAULTED=3`). `%i` is Klipper's signed 32-bit encoding of `km_result_t`: `KM_ERR_UNAVAILABLE` while `IDLE` or `WAITING`, `KM_OK` while `READY`, otherwise the latched failure. The query does not run the clock, the board, or the task. `km_diagnostic_get_state` and `km_diagnostic_get_result` read the same latched fields and may report `FAULTED` when the scheduler is already in shutdown.

`km_diagnostic_detail_query challenge=%u` (also `HF_IN_SHUTDOWN`, read-only) says where a faulted startup stopped: `km_diagnostic_detail challenge=%u step=%c lane=%c cause=%i reason=%c pin0=%hu role0=%c lane0=%c pin1=%hu role1=%c lane1=%c`. `step` is `enum km_startup_step` (`mcu/board_startup.h`, exported as the `km_startup_step` enumeration): a step before the board began (clock, identity, calibration, deadline) or the board step last entered, with `lane` for per-lane steps (`0xff` otherwise). `cause` is that step's own result, for example a lane's TMC activation `KM_ERR_TIMEOUT` rather than the latched `KM_ERR_FAULTED`. For the pin map and H723 resource steps, `reason` is the `km_resource_diag_reason_t` and up to two offending pins arrive as pin number, `km_pin_role` and lane (`pin=0xffff` when unknown). The host sends it only after `km_diagnostic_state` reports `FAULTED`.

## Hardware still pending

The task waits until `km_clock_get_state()` is `READY` and `km_boot_identity_get` returns `KM_OK` with a nonzero id. `UNAVAILABLE` from either side keeps waiting inside the same deadline. Any other error, a zero id, or clock fault or shutdown latches `FAULTED`. Identity comes only from that provider, or in a host-epoch build only from the bound host epoch. This glue does not restart the provider's own startup hook and does not invent a time fallback. An uninitialized id or a partial core is never passed to attachment.

H743/H750 use the same shared provider with an H7 clock check; see
[boot identity](../docs/boot-identity.md). Their PWM and ADC options remain
H723-only, and their compile, fixture and release-matrix results are not yet
recorded. F207/F405/F407/F765 support here is compile-tested and native-fixture-tested, but remains
experimental and is not physically qualified. This provider is intentionally
limited to Klipper's 168 MHz USB PLLQ configuration; other F405/F407 clocks, USB
pin routes, topologies, powered rewind, and analog feedback remain unavailable.
The identity is a per-reset RNG sample pair after the documented startup
discard and continuous comparison. It is an opaque epoch, not a secret or a
cryptographic key. Timer-only and constant identifiers remain invalid.

`km_board_startup_begin(NULL, 0, remaining_us, calibration)` runs once, in task context, with interrupts enabled. `NULL, 0` is the existing configured admission path. `calibration` is NULL for switched feedback; for DiffA/DiffB the task requires the published calibration object before begin and faults without board setup if it is absent. `remaining_us` is the positive time left on the original raw-tick deadline, truncated to whole microseconds. The task then calls `km_board_startup_service` while the board is pending, and it trusts board state and board result rather than a single `KM_OK`. An immediate `READY` begin is accepted. The core pointer comes from `km_board_startup_get_core` only after the board is `READY`.

A preexisting board, or any begin result other than success, is not adopted and is not cleaned up here. Begin already handles its own partial failure and retained claims. Ownership starts only when begin returns success. After that, a timeout or error calls `km_board_startup_shutdown` for this instance. A foreign instance is left to its owner. Shared shutdown dispatch already runs every `DECL_SHUTDOWN` hook, so this hook does not shut a foreign board, does not release claims, and does not reset components.

Elapsed time uses unsigned 32-bit subtraction of a fresh `timer_read_time()` against the trigger stamp, including the exact `>=` timeout tick and wrap. The scheduled wake time is not the deadline. The one-millisecond timer only wakes the task. It does not service hardware, send replies, or attach commands. It is not left armed after `READY` or `FAULTED`. Timer-queue changes run with interrupts disabled. Board, clock, identity, and `km_commands_attach` run with interrupts enabled. The task does not busy-wait, block, or replay a completed step.

After a ready board, and after another clock, deadline, and shutdown check, the task calls `km_commands_attach(core, verified_id, km_controller_changed, false)`. The last argument stays false in both builds. Only a successful attach may publish diagnostic `READY`. A failed attach, including a duplicate external binding (`KM_ERR_BUSY`), faults this diagnostic and safe-offs the owned board. That binding is not taken over. With opt-in disabled, both firmware permission APIs refuse START and `km_start` stays unavailable. With opt-in enabled, the task checks the ready board and clock again, publishes `READY`, then grants START permission through the firmware-only command API. The command handler checks a bounded in-memory board-ready callback on every START; loss of readiness permanently revokes permission. Core and driver faults are checked during the same admission. If the grant or following board check fails, the task faults, revokes permission and safe-offs the owned board. No host command can grant permission. A late attach never grants permission. Global shutdown and every diagnostic owned-board safe-off revoke permission permanently until MCU reset.

Shutdown or a missed deadline during begin, service, or attach must not write `WAITING` or `READY` over a latched `FAULTED`. After a successful attach, the task checks the deadline and shutdown once more before publishing `READY`. If that check fails, the diagnostic stays `FAULTED` and the owned board is safe-off, while the read-only command attachment can remain until MCU reset. This module does not invent an unbind or call `km_commands_shutdown`.

`DECL_SHUTDOWN` latches `FAULTED` even when the host never triggered startup. The latch survives `sched_clear_shutdown`. The hook does not read the clock, does not rearm a timer (the scheduler has already cleared user timers), and keeps the first meaningful diagnostic error.

Saved factories that this board cannot support still fail inside begin, and that error is stored. DiffA/DiffB uses the separately configured, validated calibration object on H723 local ADC builds; no calibration table is compiled into this diagnostic source. Outputs are initialized inactive by the existing board path. None of these software checks is a hardware qualification.
